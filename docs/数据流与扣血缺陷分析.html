Poketoilet 携带物战斗效果：数据流全解 与 “说了扣血却没扣血” 的根因

适用版本：cobblemon-ext 1.0.0（MonsterTrainer 模式）· MC 1.21.1 / NeoForge 21.1.240 / Cobblemon 1.7.3

〇、先记住一句话

Showdown 引擎是战斗状态的唯一权威（裁判），Cobblemon 只是舞台。 任何“扣血 / 降速”想被玩家看见并被战斗系统承认，必须走完一条完整的链路—— 在裁判的账本上记账，并由裁判向舞台广播一条协议消息。缺任何一环，数据就是孤儿。

一、两个运行时

Java / NeoForge 侧

Cobblemon = 舞台导演

世界实体、模型动画、战斗 UI、队伍存储。
我们之前的 Java 镜像数据（currentHealth、statChanges）也在这里—— 但它只是镜子，不是本体。

JavaScript / GraalJS 侧

Showdown 引擎 = 裁判

速度先后、伤害骰、命中、克制、特性道具状态。
解包在 minecraft/showdown/，跑在 GraalJS 上下文里， 线程名 "Cobblemon Showdown"。

两边的桥：GraalShowdownService。Java → JS 用 send(battleId, lines)（公开 API）；JS → Java 用协议文本行， 由 ShowdownInterpreter 解析成指令后跳回服务器主线程执行。

二、一回合的完整数据流（以番泻叶触发为例）

Java·玩家 选技能 → 打包成选择协议发给引擎
JS·引擎 Showdown 判定速度先后 → 命中 → 伤害骰 → 产出协议文本行： |move|p1a: 烈空坐|ancientpower、-damage|...、-unboost|...
Java·解释器 ShowdownInterpreter 逐行解析 → 生成 MoveInstruction / DamageInstruction / BoostInstruction 指令队列，跳回服务器主线程
Java·指令执行 逐条执行：播放动画、更新血条、画速度箭头、写战报文本流
cobblemon-ext 我们的 MOVE_USED Mixin 挂在 MoveInstruction 尾部——此刻番泻叶才“知道”出招了，然后发送 >cobblemonext_boost 协议行让引擎补一个真 boost

注意第 4 步：引擎吐出的每条协议行都会被解释器“翻译成现实”。 这条链既是显示的来源，也是数据同步的来源——后面出的问题就出在这。

断链的精确位置

Showdown 的设计分工：在原版对战流程里，招式伤害分两步走——

1. pokemon.damage(46, source)   ← 引擎底层：只改 hp 数值、检查濒死
2. battle.add('-damage', pokemon, hp文本) ← 招式结算层：广播协议消息

我们绕过了招式结算层（直接从 Java 发协议行触发），只做了第 1 步。 没有第 2 步的 -damage 消息，Cobblemon 的解释器就收不到 “该同步血量了”的通知——于是：

  • 战斗界面的血条纹丝不动（UI 由 DamageInstruction 驱动）；
  • Java 侧 Pokemon.currentHealth 不更新，战斗结束后血量不保留；
  • 而 Java 战报里“扣了 46”是我们自己打印的聊天消息，不是引擎的账本。

四、修复：一行补齐消息链

// cobblemon_ext_patch.js — cobblemonext_damage 处理器
var dmg = Math.min(amount, target.hp - 1);   // 保底留 1 HP
if (dmg > 0) {
  target.damage(dmg, target);                        // ① 裁判记账
  this.battle.add('-damage', target,
      target.getHealth());                           // ② 向舞台广播 ← 新增的一行
}

battle.add('-damage', ...) 会把消息写回战报流， Cobblemon 的解释器照常解析 → 血条即时更新 → currentHealth 持久化。 番泻叶的 -unboost 一直是手动补发的（所以它的提示/箭头正常）—— 火龙果只是漏了同样的补发。

五、几个容易混淆的点

Q：为什么无头测试全是绿的，游戏里却没效果？
无头测试断言的是引擎对象自身（p1.hp === hpBefore - 50）—— 那一层确实成功了。它没有断言“消息已广播”“UI 已同步”，所以测不出断链。 测试绿 ≠ 链路通，断言必须覆盖完整链路的每一环。

Q：为什么叫“镜像数据”？
Java 侧的 Pokemon.currentHealth / BattlePokemon.statChanges 是裁判账本的舞台复制品：正常流程里由解释器根据协议消息更新。 我们直接改复制品，裁判不知道，下一次报数就会把复制品“掰回去”（回跳现象）。

Q：那为什么保底 1 HP 还是有意义的？
因为 -damage 消息我们补发了，解释器会同步血量——但打倒（faint） 的回合结构仍由裁判管理，开场直接把一只打倒会让后续指令流错乱， 所以“不直接打倒”是刻意保留的安全边界。

Q：番泻叶的速度下降现在是“真”的吗？
是。boostBy 之后我们补发了 -unboost 消息， 解释器会画速度下降箭头；且 boost 本身记录在引擎的 boosts 里， 出手顺序真实受影响。叠加上限 -6 来自引擎规则。
